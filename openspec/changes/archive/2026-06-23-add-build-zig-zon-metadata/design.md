## Context

`xorot` is currently a small Zig CLI with a working `build.zig`, tests, and release packaging, but no `build.zig.zon` manifest. That means the repository has no canonical Zig package identity, no package-level version source, and no explicit package file boundary for hashing and downstream fetch/use.

The repository is currently CLI-only from a packaging perspective. It does not expose a Zig module or library artifact for downstream imports, and this change does not attempt to add one. The goal is limited to making the project a well-formed Zig package with explicit metadata.

The relevant project constraints already decided are:

- package name should be `xorot`
- package version should become `0.3.0`
- minimum supported Zig version for the manifest should be `0.16.0`
- external Zig dependencies remain empty
- package file inclusion should be explicit rather than implicit
- the package fingerprint should be generated by Zig and then committed as the stable identity

## Goals / Non-Goals

**Goals:**
- Add a root `build.zig.zon` manifest that is valid for Zig `0.16.0`.
- Establish `0.3.0` as the canonical package version in package metadata.
- Declare the package identity as `.xorot`.
- Constrain the package contents to the intended repository files used for hashing and downstream fetching.
- Preserve current CLI behavior, build behavior, and release workflow.

**Non-Goals:**
- Expose `xorot` as a reusable Zig library or module for downstream imports.
- Add runtime `--version` reporting or thread the package version into compiled code.
- Change `build.zig`, release targets, tests, or CLI semantics beyond what is needed for manifest generation.
- Introduce dependencies or broader packaging workflow changes.

## Decisions

### 1. Add a minimal `build.zig.zon` manifest at repo root

The manifest will be added as a new root file because Zig package metadata belongs alongside `build.zig` and defines the package boundary for the repository.

Chosen shape:

```zon
.{
    .name = .xorot,
    .version = "0.3.0",
    .minimum_zig_version = "0.16.0",
    .dependencies = .{},
    .paths = .{
        "build.zig",
        "build.zig.zon",
        "src",
        "README.md",
        "LICENSE",
    },
}
```

Rationale:
- this is the smallest manifest that still captures the package identity, version, compatibility signal, dependency set, and package file boundary
- `minimum_zig_version` is the correct field name for current Zig documentation
- `paths` should be explicit so package hashing includes only the intended project files

Alternatives considered:
- omit `paths` and rely on defaults: rejected because explicit package boundaries are clearer and are the recommended packaging posture
- include more repository files such as `Taskfile.yml`, `flake.nix`, or `openspec/`: rejected because they are not needed to build or consume the Zig package itself

### 2. Keep the package CLI-only for now

This change will not add `b.addModule(...)`, `b.addLibrary(...)`, or a public Zig API surface.

Rationale:
- the current request is only to add package metadata with version `0.3.0`
- exposing a library would require API design, source refactoring, and downstream compatibility decisions that are materially broader than this change

Alternatives considered:
- expose both CLI and library now: rejected as unnecessary scope growth for a metadata-only change

### 3. Use Zig's suggested package fingerprint

The initial manifest should omit `.fingerprint`, then a normal `zig build` should be run once so Zig reports the required fingerprint and suggests the toolchain-generated value. That suggested value should then be copied into the manifest and committed as the stable package identity.

Rationale:
- this keeps the value toolchain-derived rather than invented locally
- it matches observed Zig `0.16.0` behavior, which validates and suggests the value but does not persist it automatically

Alternatives considered:
- hand-author an arbitrary fingerprint: rejected because the toolchain owns this value
- leave fingerprint permanently absent: rejected because Zig `0.16.0` rejects the manifest without it and a stable package identity is one of the primary benefits of adding the manifest

### 4. Do not wire package version into runtime code in this change

Although Zig `master` can access `@import("build.zig.zon").version`, the project is targeting Zig `0.16.0`, and runtime version reporting was explicitly deferred.

Rationale:
- keeps this change minimal and aligned with the selected scope
- avoids mixing package metadata work with CLI feature work

Alternatives considered:
- add runtime version reporting now through build options or a generated module: rejected because it is not necessary for package metadata correctness

## Risks / Trade-offs

- [Fingerprint capture requires one validation/build failure first] -> Mitigation: implementation should run `zig build` immediately after adding the file, copy the suggested fingerprint value, and rerun the build before commit.
- [Explicit `paths` may exclude a future file needed by package consumers] -> Mitigation: keep the allow-list small now and update it intentionally when the package surface changes.
- [Downstream users may assume package metadata implies library importability] -> Mitigation: document in the proposal/design that this change adds package identity only, not a public Zig module.

## Migration Plan

1. Add `build.zig.zon` without a fingerprint.
2. Run `zig build` using Zig `0.16.0`.
3. Copy Zig's suggested `.fingerprint` value into `build.zig.zon`.
4. Verify the build succeeds with no behavior changes.
5. Commit the manifest including the toolchain-suggested fingerprint.

Rollback is simple: remove `build.zig.zon` if the manifest causes an unexpected packaging or toolchain issue.

## Open Questions

- None for this scoped change. Library/module exposure and runtime version reporting are intentionally deferred to a future change if needed.
