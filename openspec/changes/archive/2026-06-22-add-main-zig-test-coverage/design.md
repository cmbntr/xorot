## Context

`xorot` is a small streaming CLI, but nearly all of its behavior lives in two compact functions: `rot` and `xorot`. That makes the implementation easy to read but also easy to regress because the important behavior is concentrated in byte-range boundaries, stream chunking, and the rolling `u8` XOR index.

The existing build already exposes `zig build test`, so the change can stay within Zig's native test runner. The main design question is how far to push coverage without adding brittle or heavyweight infrastructure for a tiny repository.

## Goals / Non-Goals

**Goals:**
- Add direct unit coverage for `rot` and behavioral coverage for `xorot`.
- Protect deterministic edge cases such as empty input, ASCII boundary ranges, chunk boundaries, and index wraparound.
- Add randomized/property-oriented tests that validate invariants over many generated byte streams.
- Add a fuzz-friendly path that can be run repeatedly in development and remain compatible with normal Zig test execution.

**Non-Goals:**
- Changing the `xorot` algorithm or CLI behavior.
- Introducing large external test frameworks unless Zig stdlib proves insufficient.
- Building a separate long-running fuzzing service or complicated CI matrix in this change.

## Decisions

### Decision: Keep tests close to `src/main.zig`
Place tests in or directly adjacent to `src/main.zig` so private functions such as `rot` and `xorot` can be exercised without widening API surface solely for tests.

Alternatives considered:
- Separate black-box integration-only tests: weaker coverage for `rot` boundaries and internal wraparound behavior.
- Exporting helpers publicly for tests: unnecessary API expansion.

### Decision: Use layered coverage
Implement three layers of tests:
- Example-based unit tests for exact known outcomes.
- Boundary and chunking tests for stream semantics.
- Randomized/property-oriented tests that compare output against a simple reference implementation or verify stable invariants.

This keeps failures diagnosable while still broadening input coverage.

Alternatives considered:
- Only hand-written examples: too narrow for binary and chunk-boundary behaviors.
- Only randomized tests: harder to diagnose and weaker as executable documentation.

### Decision: Treat fuzzing as deterministic, stdlib-driven stress tests first
Use Zig test code to generate many varied byte sequences from seeded randomness and run invariant checks in-process. If the toolchain supports more specialized fuzz integration later, the initial structure should still be reusable.

This avoids committing the repo to external fuzz infrastructure while still giving the project a practical fuzz-style safety net.

Alternatives considered:
- Integrate third-party property/fuzz libraries immediately: more setup cost than value for this repository size.
- Skip fuzzing entirely: misses the user's explicit request and leaves binary-input robustness underexplored.

### Decision: Encode invariants around behavior, not implementation details
Property tests should validate semantics such as determinism, chunk-boundary independence, output length preservation, and consistency with a straightforward reference transform, rather than incidental details like local buffer layout.

Alternatives considered:
- Asserting internal loop mechanics directly: brittle under harmless refactors.

## Risks / Trade-offs

- Randomized tests can become flaky if seed handling is not deterministic -> Use fixed seeds by default and allow optional higher-iteration local stress runs later.
- Fuzz-style loops can slow normal test runs -> Keep default iteration counts modest and isolate heavier stress coverage behind clearly named tests or build steps.
- Testing private streaming logic may require lightweight test harness helpers -> Keep helpers minimal and local to test code.
- Computing expected outputs for long vectors by hand is error-prone -> Prefer a compact reference implementation inside tests for randomized comparisons.

## Migration Plan

No runtime migration is required. Implementation should land as additional test coverage and any small build-step updates needed to expose the tests. Existing developer flows should continue to work with `zig build test`.

## Open Questions

- Whether Zig 0.16's current stdlib/testing facilities are sufficient for the desired fuzz loop ergonomics, or whether the change should stop at deterministic property-style randomized tests.
- Whether heavier fuzz/stress runs should be part of the default `test` step or exposed as a separate optional build step to preserve fast feedback.
